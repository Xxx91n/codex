# 发行列车规格

- 状态：2026-10-18 定稿（本轮 grill 产物）
- 规则依据：[ADR-0016](../../adr/0016-release-train-and-branch-base.md)（本文的裁决源）；[ADR-0012](../../adr/0012-release-branching-scheme.md)（命名与标签；其「基点 = tag 提交」条款已被 ADR-0016 修订）
- 性质：行为规格。执行任务拆解见仓外任务书；本文件不写执行排期。

## 0. 一句话

每个上游稳定版产出一条 fork 发行分支，按版本号升序逐格做完；每格交付三平台资产与独立 release 页。

## 1. 范围（R-01）

- 维护起点：`0.162.1`。
- `0.162.1` 之前的历史版本：不建分支、不补发行。
- 每格产物必须是含 fork 修改的版本（三 wire 能力在位），不得是上游原样。
- 禁止产出“当前 fork 代码 + 旧版本号”的伪发行版。

## 2. 单版完成判据（R-02）

六项同时具备才算完成：

1. 分支 `tri/vX.Y.Z`
2. Cargo 版本字段 `X.Y.Z-tri.N`
3. 标签 `tri-vX.Y.Z-tri.N`
4. 三平台资产：win-x86_64 / linux-x86_64 / mac-aarch64
5. 该版独立 release 页
6. 四门全过：注册点 grep / CI 构建 / 定向测试 / checksum 家族

只有“分支存在 + CI 绿”不算完成；多版资产塞进单一滚动页也不算完成。

## 3. 版本号与标签（R-03）

- 形式：prerelease `X.Y.Z-tri.N`，不用 build metadata；标签不得用 `rust-v` 前缀。
- 消耗 N 的触发：分支上任何会改变产物内容的提交（代码、Cargo 版本字段、构建脚本、依赖锁）。
- 不消耗 N 的动作：CI 重跑、资产重传、release 页说明编辑。
- 已推送的 tag 永不移动、永不覆盖、永不复用。
- 每格的 N 从 1 起；`0.162.1` 的首次正式发行即 `tri.1`。

## 4. 分支拓扑（R-04）

- trunk = `tri-wire-api`；版本分支从 trunk 切出，不从上游 tag 切。
- 版本分支内完成发行；发行后即冻结。
- 发现该版没改好：回到该版本分支继续修（消耗新 N），trunk 临时与该分支同步吸收修复。
- 该版彻底没问题后，trunk 恢复与上游同步，进入下一版。
- 禁止“完全同步”：不得用上游内容覆盖 fork 修改。

## 5. 每格固定步骤（R-05）

1. 算切点：`cut = merge-base(<tag>, upstream/main)`。
2. 确认 trunk 已合到 `cut`（含）；未合先合（按 R-06/R-07）。
3. 从 trunk 上“已含 cut”的提交切 `tri/vX.Y.Z`。
4. 把 `cut..<tag>` 的提交 cherry-pick 进来；跳过上游版本号提交，用我们自己的 `X.Y.Z-tri.N`。
5. diff 门：`diff(<tag>, 版本分支)` 必须恰好等于 fork 修改集；多一个文件即漂移，停。

禁止从 trunk 当前 HEAD 直接切；禁止跳过 diff 门打 tag。

## 6. trunk 吃上游（R-06）

- 操作：merge。每次同步 = 一个合并提交，保留双线历史，冲突解一次，历史永不重写。
- 禁止 rebase（SHA 重写，已发版本分支与 tag 会脱钩）。
- 禁止 squash 上游历史（丢失提交粒度）。
- 禁止自动合并：上游内容进入 trunk 必须逐处裁决（R-07）。

## 7. 冲突裁决（R-07）

每次同步先列出真实冲突文件集；命中白名单的按表裁，未命中的一律停手报告。

| 文件 | 规则 |
|---|---|
| `codex-rs/Cargo.lock` | 整份取上游，仅改自身 crate 版本行 |
| `codex-rs/Cargo.toml` | 依赖与 feature 取上游；`version` 用我们的；fork 新增依赖保留 |
| `codex-rs/codex-api/src/common.rs` | wire 常量与 IR 扩展保留，上游新字段并入 |
| `codex-rs/core/src/client_common.rs` | `ResponseStream` / `PreemptSeam` 保留，上游改动并入 |
| `codex-rs/core/src/tools/registry.rs` | namespace 限定名回环保留 |
| `codex-rs/core/src/tools/spec_plan.rs` | tool_search 仅 Responses 的判据保留 |

白名单是活表：新增冲突文件必须经人确认后入表，不得由执行者自行判断。

## 8. 发版前置门（R-08）

两项均修完并合入 trunk 后，才允许切版本分支与打 tag：

1. Issue #2：TUI 下 `wire_api = chat` 不得报错，与 exec 行为一致。
2. Anthropic file-id 图片：`ImageReference::File` 不得静默丢弃，需真实上送。

其余已知债（transport 重复 / pause_turn 未实测 / 事件顺序）不阻塞发行。

## 9. 执行者权限（R-09）

适用于任何执行者（人、本地 agent、bot）：

1. 可自主：建分支、合并、cherry-pick、打本地 tag、跑 CI。
2. 门禁后可行：推 `tri/v*` 分支、推 `tri-v*` tag、发 release——仅当 diff 门与 CI 门脚本均返回零。
3. 永远禁止：改默认分支、删已发版本分支或 tag、动 `origin/main`、改 `.github/workflows`、改 `.gitattributes`、碰真实 `~/.codex`。

原则：凡“要不要继续”的判断必须落成可执行脚本，以退出码为准；执行者不做主观判断。

## 10. main 镜像与两条管线（R-10）

- `main`（本地 + 远端）= 上游 `main` 纯镜像，只快进，零 fork 提交，不参与发行。
- `tri-wire-api` = 工作区，永不自动合并上游。
- “让 main 跟上上游”与“让 trunk 吃上游”是两件事，不得写在同一句流程里。
- main 的同步：定时 workflow（每日一次）执行 `git push origin upstream/main:main`，不带 `--force`；快进不了就失败报错。
- 禁止用 GitHub 的 “Sync fork” 按钮（它同步默认分支，会试图用上游覆盖工作区）。

## 11. 队列与顺序（R-11）

- 发行队列按版本号升序，最小在前。
- 当前格全档完成后，才允许开始下一格。
- 新版发布只是往队尾追加；不打断、不抢占、不丢弃当前格。
- 禁止跳过未完成的格。
- 首批顺序：`0.162.1` → `0.163.0`。

## 12. 自动化程度（R-12）

- 起步：半自动。每日查上游稳定 tag（`rust-vX.Y.Z`，不含 alpha/beta）；发现新版先出开工报告（切点、冲突文件集、白名单命中、前置门状态），人工确认后才动手。
- 转全自动的条件：`0.162.1` 与 `0.163.0` 两格全档跑通。
- 未满足条件不得提前转全自动。

## 13. 失败处理（R-13）

- 表外冲突 → 立即停，不重试，等人补表。
- **infra 红与代码红分开计。** 平台侧信号不计入重试计数：`exit 143` / `The runner has received a shutdown signal` / runner 被回收 / 依赖下载超时等。这类红只允许“同一作业经人批准后重跑”，不得因此停队列，也不得当作代码缺陷记录。
- 代码红（编译错、测试失败、门禁脚本非零）→ 允许重试 1 次；第二次红 → 停。
- 无法归类时一律按代码红处理（保守）。归类本身必须能用一个脚本或一条日志匹配说明，不得凭印象。
- 停下后队列停在该格，不跳到下一格。
- 停住期间只允许产出 STOP 报告（哪一格、哪一步、哪个文件、什么错误、已试过什么）。

## 14. 交付物（R-14）

- 资产名带版本：`codex-<X.Y.Z-tri.N>-<platform>-<target>.<ext>`。
- release 页正文用固定模板，不得自由发挥：

```
上游版本：rust-vX.Y.Z（切点 <sha>）
本版内容：上游该版全部内容 + 三 wire 支持 + 下列 fork 修改
fork 修改：<diff 门脚本自动生成>
已知限制：<固定段落>
校验和：<三平台 sha256>
```

- 滚动 release `tri-wire-test` 保留，但只做“最新已发布版本的索引”：只放说明与指向最新版页的链接，不重复上传资产。
- 索引页的刷新**不得依赖任何构建产物**：它只从 release 列表推导。trunk 上更新索引不跑三平台构建、不跑 e2e；trunk 的编译面由 fork-health 的 seam 作业覆盖。版本号只在 `tri/v*` 路径上从资产名反推。

## 15. bug 验收（R-15）

- Issue #2：配置解析必须接受 `wire_api = "chat"`。TUI 与 exec 共用同一个反序列化器，TUI 侧**不存在**独立的 wire 校验，也不得新增；由 CI 断言（选择器 `test(chat_wire)`）防止上游 merge 把拒绝机制带回来。
- file-id 图片：出站转换不得静默丢弃。跨厂商 `file_id` 无字节可取时，降级为可见文本占位并由单测断言；真实上送只能在字节仍存在的捕获阶段完成。
- 不得用人工实测替代单测门。

## 16. 执行者状态与报告（R-16）

- 队列进度不存储、不建状态文件：从 tag 推导——上游存在 `rust-vX.Y.Z` 且本 fork 无对应 `tri-vX.Y.Z-*` tag，即该格未完成；最小未完成格 = 当前格。
- STOP 报告：`gh issue create`，打标签 `stop-report`，正文按 R-13 固定格式（哪一格、哪一步、哪个文件、什么错误、已试过什么）；沿用 fork-health `alert` 作业的既有模式。
- 开工报告（R-12 半自动阶段）：发到人机对话通道，人工确认后才动手；不落仓内文件。
- 禁止维护任何形式的状态文件（仓内或仓外），禁止把状态写进 AGENTS.md / CONTEXT.md。
## 17. 负向需求汇总

- 不回溯 `0.162.1` 之前的版本。
- 不产出“当前代码 + 旧版本号”。
- 不 rebase、不 squash 上游历史。
- 不在白名单外自行裁决冲突。
- 不无限重试、不跳过失败格；但也不把 infra 红当代码红停队列（R-13）。
- 不让索引页刷新挂上任何构建产物（R-14）。
- 不用上游覆盖 fork 修改。
- 不移动/覆盖/复用已推 tag。
- 不让滚动页成为第二个真相。
- 不在两格跑通前转全自动。
- 不维护任何状态文件（队列从 tag 推导，R-16）。
